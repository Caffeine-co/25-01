# v2.0 实验与迭代分析（本地实际运行）

## 1. 复现命令与原始数据

```bash
python -m unittest discover -s tests -v
python scripts/benchmark.py             # 兼容行为基准
python scripts/stress.py                # 30 种扰动 × 7 天
python scripts/production_benchmark.py  # 6 场景 + 60 随机初值 × 7 天
python scripts/smoke_server.py          # 子进程启动、HTTP、重启恢复
python scripts/verify.py                # 全部执行并写 results/verification.json
```

新实验数据位于 `results/v2/`：六个场景的 `.db`、六小时采样 `.csv`、汇总 `metrics.json` 和 `stress_60seeds.csv`。兼容性基准与 30 种外部扰动记录位于 `results/summary.json`、`results/stress_summary.json`。所有计数都来自实际 `WorldRuntime` 输出，并且日志由 SQLite 持久化。

## 2. 六个场景长期运行结果

| 场景 | 模拟时长 | 审计事件数 | 项目完成 | 项目步骤失败 | 其它观测 |
|---|---:|---:|---:|---:|---|
| `art_project` | 7 天 | 336 | 1 | 0 | 4 步绘画项目顺利完成 |
| `art_project_disrupted` | 7 天 | 344 | 1 | 2 | 绘画设施在 t=300 失效，t=900 恢复；项目继续成功 |
| `apartment_with_knowledge` | 7 天 | 325 | 0 | 0 | 错误传闻最终被两次直接观察修正 |
| `apartment_sustainable` | 30 天 | 1356 | 0 | 0 | 单人物完成 59 次技能练习，绘画技能约 49.20 |
| `roommates` | 30 天 | 2670 | 0 | 0 | 双人物合计练习 118 次、社交 29 次 |
| `apartment_scarce` | 7 天 | 90 | 0 | 0 | 资源有限时，人物 vitality 最终降到 0，无虚构库存补给 |

**注意：没有预配置多步骤项目的场景，其“项目完成=0”是符合预期的，不是角色没有活动。** 项目完成数只统计 `project_completed` 事件，普通练习和长期技能达标单独计数。

双人物场景中，两人的双向信任最终均约为 **0.7514**（29 次关系更新），没有轻易达到 1。它反映的是数值机制抑制饱和的效果，不能据此证明真实人类关系可信度。

## 3. 故障注入与修复效果

### A. 项目行动过程中设施停用

- t=254 启动练习，t=300 设施停用。
- t=344 行动结算失败，项目 `index` 不变。
- t=524 再次尝试，t=614 失败；两个项目步骤失败事件均入日志。
- t=900 设施恢复，此后角色能够继续练习，项目最终 4/4 步完成。

`art_project_disrupted` 累计共有 **3 次普通动作失败**，其中 **2 次属于项目步骤失败**；另一次来自独立的承诺练习。将其混为“3 次项目失败”是不准确的。

### B. 证据冲突与改判

先将 `meeting_place=park` 作为外部传闻，置信度 0.6。t=120 真实观察 `studio`，t=600 真实观察 `kitchen`。最终个人信念是 `kitchen`（来源 `world_observation`，置信度 1.0），历史证据仍保留先前传言与观察。客观地图从未因为这些个人信念而变化。

### C. 运行服务的线程安全缺陷

第一轮 HTTP 自动测试出现 `sqlite3.ProgrammingError: SQLite objects created in a thread can only be used in that same thread`，表现为多个 API `500`。原因是 HTTP worker 线程使用了主线程创建的 SQLite 连接。修复为 `check_same_thread=False`，**且所有 RuntimeService 的读写均由 RLock 串行化**，并在 SQLite 事务中执行版本检查。重新测试 HTTP 与并发请求后通过。

### D. 项目长时间运行与恢复

恢复测试会在项目进行中创建快照，并继续执行；与单次运行相比状态一致，且快照之后的事件序列一致。早期测试错误地拿“全程事件日志”与“快照之后的事件日志”比较，修正实验对照口径后通过。

### E. HTTP 断线与重复请求

并发发送 24 个**内容与幂等 ID 完全相同**的时间推进请求，所有返回同一已提交结果，世界只前进 30 分钟。使用相同 ID 提交不同数据返回 `409`；数据库重启后旧请求回执仍可查询。不同数据库写入者持旧 revision 修改同一 DB 时，旧版本写入被拒绝。

## 4. 随机扰动与确定性复验

两组独立测试：

- 旧基准：`scripts/stress.py`，30 种固定种子，分别给持续生活场景安排 9 次随机设施停用/恢复、身体冲击和外部消息，每组 7 天；均通过分段/整体运行一致性。
- 新基准：`scripts/production_benchmark.py`，60 种不同需求和 vitality 初值，项目场景加入可恢复的设施故障，每组 7 天；**60/60** 组单次与分段运行的快照、事件序列一致，**60/60** 项目完成，项目步骤失败次数范围 **1～2**，审计事件数范围 **322～368**。

这些数据表明：在上述受控场景与参数范围内，事件推进、失败恢复和项目结算具备良好确定性。它们**不能**说明系统具备真正开放世界自适应能力，也不能用作现实心理真实性证据。

## 5. 可用性与模型服务验收

`tests/test_production.py` 包含真实本地 HTTP 请求、认证失败、幂等去重、无效操作回滚、跨进程/连接竞争、数据库备份、结构化反思、模型非法动作拒绝，以及一个本地假 `/chat/completions` HTTP 服务。`scripts/smoke_server.py` 还实际以**子进程**启动 `worldlife-server`，发送聊天/推进请求，停止并重启，验证世界分钟和历史请求回执仍可恢复。

**未实测**：第三方真实模型质量、供应商认证和费用；跨国网络抖动；Windows 服务托管；千人并发；真实 QQ/游戏的外部发送；人类主观评价。

## 6. 最终研究判断

相较 v1.0，最大进步不是“模拟更真实”，而是**工程运行链条更加完整**：多步项目有可验证的完成证据，信念有证据来源，外部服务有认证与持久化去重，重启和并发异常有明确语义。这足以作为可部署、可继续开发的**小规模本地虚拟人物系统**，但仍不应把现阶段的数值心理与固定社交选择视作真实人格。
